# Security policy

## What this project is, before you rely on it

**Graticula has been released once and has never been deployed by anybody but its
author.** ~~There is no published image, no versioned release, and no deployment in
production anywhere.~~ **Corrected 2026-09-09**, and the old sentence had been false
for a week: `v0.1.0` was tagged on 2026-09-02, its release workflow succeeded, and it
published two images to GHCR — `graticula` and `graticula-datastore`, both also tagged
`latest` (`docs/architecture-debt.md`, D-19, closed on that release). This repository
is public.

What has **not** changed is the part that matters to a reader deciding whether to run
it: **nobody has deployed this in production**, and one tag is not a track record. The
honest security posture of a product on its first release is that its unknown flaws
have not been found yet rather than that it has few.

That said, the code is real, it holds credentials and it answers network
requests. So this policy exists now rather than at the first release, because a
security contact that appears after the first report is a contact that was not
there when it was needed.

## Reporting a vulnerability

**Please do not open a public issue.**

Use GitHub's private vulnerability reporting on this repository — the
**Security** tab, then **Report a vulnerability**. It creates a private advisory
that only the maintainers can see, and it is the preferred route because nothing
about it depends on an inbox being watched.

If that is unavailable to you, email **erdincyildiz@gmail.com** with `graticula
security` in the subject.

Please include what you need to include for the report to be actionable: the
version or commit, what an attacker gains, and the smallest thing that
demonstrates it. A proof of concept is welcome and is never required — a clear
description of a flaw you have not weaponised is still a report worth making.

## What you can expect

| | |
|---|---|
| **Acknowledgement** | Within 7 days. If you have not heard back in 14, assume the message was lost and send it again. |
| **Assessment** | Within 30 days: whether it is a vulnerability, how severe, and what the fix looks like. |
| **Fix** | We aim for 90 days from the report. |
| **Disclosure** | Coordinated. The advisory is published when the fix is, or at 90 days, whichever is first — and if the deadline arrives without a fix, the advisory is published anyway saying so. |
| **Credit** | Yours, by the name you ask for, unless you would rather not be named. |

**These are commitments made by one person, and that is the honest limit of
them.** This project is maintained by its author in the open, not by an
organisation with a rota. If a report arrives while that person is unavailable,
the dates above will slip, and the 14-day rule above exists precisely so that a
silent inbox does not leave you waiting indefinitely. When the project has more
than one maintainer this section gets rewritten with the arrangement that
replaces it.

## Scope

**In scope** — anything in this repository that runs on a server: the host, the
providers, the platform store schema and migrations, authentication and
authorization, the tile and feature paths, the geometry service and its overlay
worker, and the parsers, which are the most likely place for something to go
wrong because they read attacker-controlled bytes.

**In scope and worth saying out loud**, because they are deliberate trade-offs
already written down rather than oversights, and a report that they exist is
not news — a report of a way *past* them very much is:

- Archives are decompressed under five bounds
  (`docs/adr/ADR-024-shapefile-import.md`). The bounds are the defence.
- The browsing session cookie authenticates `GET` and `HEAD` only
  (`docs/security.md`). A way to make it authenticate anything else is a
  vulnerability.
- ArcGIS compatibility puts credentials in URLs (`docs/security.md`). Bounded,
  not fixed.
- Overlay runs in a worker process with a deadline and a heap ceiling
  (`docs/adr/ADR-022-geometry-server.md`). A way to survive the deadline, or to
  take the parent down with the child, is a vulnerability.
- The geometry service accepts a request of up to 500,000 vertices and up to
  Kestrel's body ceiling, and **a request large enough to be refused costs about
  four seconds of CPU to refuse** — measured, `docs/architecture-debt.md` D-188. That
  cost is known and unpaid rather than unnoticed, so a report that a big body is
  expensive is not news; a way to make it *cheaper for the caller than for the
  server by a wider margin than that* is.

**Out of scope** — `/experiments` and `/benchmarks`, which are disposable and
never promoted; `compose.yaml`, which is for development, takes its password
from `GIS_DATASTORE_PASSWORD` and says in the file that the default is
development only; findings that require an attacker to
already hold administrator credentials; and reports generated by a scanner with
no analysis of whether the finding is reachable.

**Dependencies** are not in scope here — report those upstream. If an upstream
advisory affects a deployment of this project, tell us anyway and we will treat
it as an update to ship rather than a flaw of ours.

## Supported versions

~~There are no supported versions, because there are no versions.~~ ~~**There is one, as
of 2026-09-02.**~~ **There is one line, `1.0.x`, and it moves on every commit — 2026-09-10.**

| Version | Supported | What that means |
|---|---|---|
| `1.0.x` | **Yes**, the newest | The current release line, and it advances on **every commit** — owner decision, 2026-09-10. A security fix lands on `main` and is published within minutes as the next `1.0.z`, which rebuilds both images. |
| Older `1.0.z` | — | Superseded rather than supported. With a release per commit there are many of them and none is a maintained line; the fix is always in the newest. |
| `main` | **Yes** | Where a fix lands first, and with a release per commit it is never more than one commit ahead of the newest tag. |
| `0.1.0` | — | The first tag this project ever had, 2026-09-02. Not maintained. |

**A release per commit is not a support policy either, and it is a different way of not
being one.** There is no long-term-support branch, no backport commitment and no published
end-of-life date. What replaces them is narrower and easier to keep: **there is only ever
one version worth running, and it is the newest**, because a fix reaches a published image
within minutes of landing rather than waiting for somebody to decide a release is due.

**What that costs, said plainly.** An operator pinning `1.0.7` is pinning a commit, not a
tested milestone — every tag runs the same gate the quickstart runs, and none of them is a
milestone anybody paused over. If you need a version somebody stood behind, there is not one
yet; there is `main`, published continuously, and this document telling you so. When a
second line exists — a `1.1.x` while `1.0.x` still gets fixes — this table gains a row and
the promise gets harder, which is the point at which it needs rewriting rather than
extending.
